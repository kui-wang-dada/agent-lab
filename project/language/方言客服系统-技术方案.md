# 方言客服系统 — 技术实现方案

> 文档对象：B 公司技术决策人 + 商务决策人
> 版本：v1.0（基于前序产品架构 v1.1 + ASR 技术调研定稿）
> 关键背景：B 自带成熟标注团队；交付周期目标 2-3 个月

---

## 1. 方案概要（一页扫完）

### 一句话定义

**一套覆盖 20+ 主流方言的客服 ASR（Automatic Speech Recognition，语音识别）系统，上线日即可用，并能随 B 标注团队的持续投入自动扩展长尾方言、增强细分场景。**

### 核心闭环

```
        来电方说方言

             ▼
   ┌──────────────────┐
   │  LID 自动方言判断 │  ← Language Identification，自动识别"这是哪种方言"
   └─────┬────────────┘
         │
   ┌─────┴───────────────────────┐
   ▼                             ▼
┌─────────────────┐      ┌──────────────────┐
│  L1：商用 API    │      │  L2：自训层       │
│  阿里 Qwen3-ASR │      │  开源底座+LoRA微调 │
│  20+ 主流方言    │      │  长尾 / 细分场景  │
│  上线日即可用    │      │  B 标注驱动成长   │
└─────────┬───────┘      └──────────┬───────┘
          │                         │
          └────────────┬────────────┘
                       ▼
              ┌──────────────────┐
              │ 统一转写文本      │
              └────────┬─────────┘
                       ▼
              ┌──────────────────┐
              │ LLM 生成应答     │  ← 接 Qwen 大模型生成话术 / 工单 / 小结
              └────────┬─────────┘
                       ▼
                  返回客服侧
                       │
                       ▼
            ┌──────────────────────┐
            │ 通话归档 + B 标注团队 │  ← 录音 + 弱转写 → 标注 → 训练集
            └────────┬─────────────┘
```

## 2. 技术架构

### 2.1 三层混合架构（核心设计）

为什么不能"一个模型解决一切"：方言 ASR 分两个截然不同的世界——**主流方言**已被大厂训练成熟（B 自训追不上也没必要追），**长尾方言**大厂不覆盖（必须 B 自训才有）。所以采用**商用 API 兜主流 + 自训层补长尾**的混合架构是工程最优解。

```
┌─────────────────────────────────────────────────────────────┐
│  入口层：LID + 路由                                          │
│  - 短音频先做方言判断                                         │
│  - 高置信度路由到对应 ASR；低置信度走默认 + 人工标记         │
└──────────────────┬──────────────────────────────────────────┘
                   │
        ┌──────────┴──────────┐
        ▼                     ▼
┌──────────────────┐  ┌──────────────────────┐
│  L1：商用 API 层  │  │  L2：自训 ASR 层      │
│                  │  │                      │
│ • 阿里 Qwen3-ASR │  │ • 基座：FunASR /      │
│   -Flash（主力） │  │   SenseVoice 开源    │
│ • 讯飞星火方言    │  │ • LoRA-per-dialect   │
│   大模型（备份） │  │   每方言独立权重     │
│                  │  │ • Mac Studio M4 Max │
│ 责任：           │  │   64GB 本地训练      │
│ 20+ 主流方言     │  │                      │
│ 上线日即可用     │  │ 责任：               │
│                  │  │ 长尾方言 / 细分增强  │
│ 接 Qwen LLM 同生 │  │ B 标注驱动成长       │
│ 态，集成省事     │  │                      │
└────────┬─────────┘  └──────────┬───────────┘
         │                       │
         └───────────┬───────────┘
                     ▼
           ┌──────────────────┐
           │  统一文本输出     │
           │  + 置信度 + 元数据 │
           └────────┬─────────┘
                    ▼
           ┌──────────────────┐
           │  LLM 应答层       │
           │  Qwen 系列        │
           └──────────────────┘
```

### 2.2 三档方言策略

| 档位 | 方言示例 | 策略 | 上线日就能用？ | 谁负责升级 |
|---|---|---|---|---|
| **A 档（主流）** | 粤语、川渝、闽南、吴语/上海、东北、客家、湘语、赣语、晋语、河南、陕西、山东等 15-20 种 | 直接调阿里 Qwen3-ASR-Flash | ✅ | 阿里官方持续升级 |
| **B 档（细分增强）** | 粤语行业术语、闽南细分口音、特定场景术语 | 商用 API + hotword（热词）+ biased ASR（上下文偏置）+ B 数据 LoRA 增强 | ✅ 商用版立即可用；自训增强 4-6 周后陆续上线 | B 标注 + Kevin 训练 pipeline |
| **C 档（长尾）** | 温州、潮汕、客家细分、闽东等商用 API 不支持的方言 | B 标注从开源（FunASR / SenseVoice / TeleSpeech）从零训 | ❌ 需 30-100 小时标注数据后才能上线 | B 标注 + Kevin 训练 pipeline |

> **少数民族语言（藏维蒙）**：是独立语言不是方言，音系/文字/语法都与汉语无关。商用 API 没有可靠商品，数据需求是汉语方言的 3-5 倍。**本期不承诺**，作为 v2 路线图。

### 2.3 关键技术选型

| 模块 | 选型 | 理由 |
|---|---|---|
| **L1 主力 ASR** | 阿里 Qwen3-ASR-Flash | 一个 API 解决「方言 ASR + 自动 LID + 接 Qwen LLM」三件事；20+ 中文方言；与下游 LLM 同生态集成最省事 |
| **L1 备份 ASR** | 讯飞星火方言大模型 | 长尾方言覆盖更广；主 API 故障时自动 fallback |
| **L2 自训基座** | FunASR / SenseVoice（开源） | 阿里开源，覆盖 7 大方言系统；社区活跃；支持 LoRA 微调；可本地部署不外泄数据 |
| **微调方法** | LoRA（Low-Rank Adaptation） | 低参数量适配（<10% 原模型参数）；M4 Max 64GB 本地可跑；学术界已在方言 ASR 上验证 SOTA |
| **方言隔离机制** | LoRA-per-dialect | 每个方言独立权重，避免 catastrophic forgetting（灾难性遗忘——多方言挤同一组权重会互相干扰） |
| **强对齐工具** | WhisperX + wav2vec2 CTC | 词级时间戳 <100ms 误差；与标注流水线对接 |
| **LLM 应答** | Qwen 系列 | 与 ASR 同生态；中文应答能力强；可私有化部署 |
| **VAD / Diarization** | silero-vad / pyannote-audio 3.x | 录音预处理标配，自动化率 80-95% |

### 2.4 两个必须澄清的认知误区

写进文档防止后续扯皮：

#### 误区 1：「商用 API 会被 B 训练得越来越准」——**错**

阿里 / 讯飞的商用 ASR 是**黑盒**，B 不管标注多少数据、调用多少次，那部分识别能力永远停在出厂版。商用 API 只对外暴露两种"微调"接口：

- **hotword**（热词）：上传行业术语词表，让 API 在转写时优先匹配
- **biased ASR**（上下文偏置）：调用时传入上下文 prompt 引导识别方向

这两种都是**调用时参数**，不是真正的权重训练。能让 B 标注数据真正变成"模型能力"的，**只有 L2 自训层**。

#### 误区 2：「L2 自训层要把所有方言都重训一遍」——**错**

L2 自训层只服务两件事：

- **(a) 填白**：商用 API 不支持的方言（温州、潮汕、客家细分等），B 必须自训才有
- **(b) 增强**：商用 API 支持但准确率不够的细分场景（行业术语、强口音、嘈杂环境等）

**绝不**重训粤语、川渝这种主流方言——大厂用千万小时数据训出来的模型，B 用几百小时追不上，是重复造轮子。

## 4. 上线后的自动成长机制

### 4.1 数据飞轮怎么转

```
   真实通话流量
        │
        ▼
  ┌──────────────────┐
  │ 全量录音留存      │  ← 不挑挑选选，全留
  └────────┬─────────┘
           │
           ▼
  ┌──────────────────┐
  │ VAD + Diarization │  ← 自动切分 + 角色分离（80-95% 自动化）
  └────────┬─────────┘
           │
           ▼
  ┌──────────────────┐
  │ 弱转写（现成 ASR）│  ← 先跑 L1 出粗结果
  └────────┬─────────┘
           │
           ▼
  ┌──────────────────┐
  │ 强对齐（WhisperX）│  ← 音频 + 文本 → 词级时间戳
  └────────┬─────────┘
           │
           ▼
  ┌──────────────────┐
  │ B 标注团队精校    │  ← 关键步骤：人工逐字校对 + 方言标签
  │ 2-3× 音频时长     │
  └────────┬─────────┘
           │
           ▼
  ┌──────────────────┐
  │ 质检 + 入训练集   │
  └────────┬─────────┘
           │
           ▼
  ┌──────────────────┐
  │ 月度 LoRA 增量    │  ← 该方言独立权重，互不干扰
  │ 微调 + 自动回归   │
  └────────┬─────────┘
           │
           ▼
  ┌──────────────────┐
  │ A/B 灰度上线      │  ← 固定测试集回归通过才推全量
  └────────┬─────────┘
           │
           ▼
      模型更准
           │
           └──→ 回到入口，识别更准 → 标注更轻松 → 飞轮加速
```

**飞轮三个发动机**（缺一不可）：

1. **真实通话量**：单方言月通话 ≥1000 通才有效数据沉淀（按 B 业务量评估）
2. **标注产能**：50 小时高质量方言数据 ≈ 200-400 人时标注（B 自带标注团队这条已解决）
3. **训练 + 上线机制**：月度增量 LoRA + 灰度发布 + A/B 回归（Kevin 交付）

### 4.2 边际成本结构

| 维度 | L1 商用 API | L2 自训 |
|---|---|---|
| 上线日能力 | 20+ 主流方言可用 | 1-3 个起步长尾方言 |
| 是否自动成长 | ❌ 不会（黑盒） | ✅ 会（B 标注 → 训练 → 上线） |
| 新方言扩展成本 | 含在 API 调用费内（厂商支持的范围内） | 1-2 人月标注 + 系统零边际成本 |
| 调用成本 | 商用 API 计费（按音频时长） | 自有 GPU 边际成本极低 |
| 适用场景 | 主流方言 + 标准业务 | 长尾方言 + 细分增强 |

**关键结论**：B 持续投入标注 → 长尾方言库不断扩展 → 每加一个新方言 / 增强一个场景，系统侧零边际成本，只算标注人力。规模效应明显。

### 4.3 增量训练节奏建议

| 阶段 | 数据累积量 | 训练频率 | 备注 |
|---|---|---|---|
| 冷启动期（前 3 月） | 0-50 小时/方言 | 月度 | 优先把 B 存量历史数据消化 |
| 成长期（4-12 月） | 50-200 小时/方言 | 双周 | CER 进入边缘可用 → 商用可用 |
| 稳定期（12 月后） | 200+ 小时/方言 | 按需触发（数据漂移监测自动触发） | 主要做 case 漂移修正 |

**强约束**：每次训练必须跑固定测试集回归。新模型在历史方言上 CER 不许变差才能上线，**这是防止"飞轮越转越烂"的唯一保险**。

## 5. 能做与做不到的清单

诚实管理预期。下面所有承诺写进合同。

### 5.1 能做

- ✅ **2-3 个月内交付可工作的系统**，L1 主流方言上线日即可用
- ✅ **20+ 主流汉语方言**覆盖（粤、川渝、闽南、吴、东北、客家、湘、赣、晋、河南、陕西、山东、云贵等）
- ✅ **自动方言判断**（LID 路由 + 低置信度兜底）
- ✅ **方言转普通话文本** + 置信度评分
- ✅ **LLM 应答 / 工单 / 通话小结**自动生成
- ✅ **长尾方言冷启动**：依 B 存量数据，2-3 个月内首批 1-2 个长尾方言上线
- ✅ **持续成长机制**：月度 LoRA 训练 + A/B 灰度 + 自动回归
- ✅ **多方言并行**：LoRA-per-dialect 隔离，互不干扰
- ✅ **客服系统对接**：RESTful API 模式
- ✅ **数据脱敏 pipeline**：人名 / 电话 / 身份证号自动替换占位符

### 5.2 做不到 / 不承诺

- ❌ **"所有方言"**：实际可覆盖上限约 30-40 种（含 L1 主流 + L2 长尾），不存在覆盖全部地方音变的方案。"讯飞 202 方言"是营销话术，**本方案不引用**。
- ❌ **藏语 / 维吾尔语 / 蒙古语**：独立语言不是方言，数据需求 3-5 倍，本期不在承诺范围。如必须覆盖单独立项。
- ❌ **特定 CER 数值承诺**（如"必须达到 15%"）：训练效果有上限，长尾方言依数据量浮动。承诺**改善曲线**而非**绝对数值**。
- ❌ **方言夹普通话场景准确率**：比纯方言低 10-15%，但已能商用（主流厂商都标"支持混说"）。
- ❌ **极偏远 / 强噪声场景**：偏远山区强口音 + 通话噪声会显著低于实验室数据。建议先做样本测试再签效果指标。
- ❌ **"模型升级是使用量驱动的"**：错。模型升级是**标注驱动**的——B 不投标注，系统不会自己成长。这点必须在 B 内部对齐。
- ❌ **完全替换 B 现有客服中台**：本方案是"识别 + 应答能力层"，不是完整客服平台。IVR / ACD / 工单系统按 B 现有方案接 API。

### 5.3 模糊地带（需双方协商基线）

- ⚠️ **每个方言的"可用 CER 阈值"**：建议在测试集上 CER ≤ 25-30% 视为通过（参考行业经验，方言场景比普通话宽容）
- ⚠️ **LID 误判率容忍度**：5-7 主流方言场景准确率 90%+；扩到 20+ 预期 70-80%。需 UI 留"方言判断错了"反馈按钮
- ⚠️ **AI 应答覆盖率**：MVP 期 10-20% 即合格；主打"辅助"而非"替代"

## 6. 风险 + 合规边界

### 6.1 技术风险

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| LID 在 20+ 方言场景准确率下滑 | 错路由 → 转写错 | 低置信度走默认 + 人工标记；UI 留方言纠正按钮 |
| 商用 API 厂商策略变化 / 涨价 | 成本失控 | L1 双通道（阿里 + 讯飞）热切换 |
| 多方言训练 catastrophic forgetting | 新方言上线导致旧方言 CER 退化 | LoRA-per-dialect 权重隔离 + 强制回归测试 |
| 录音质量过滤折损 | 名义数据量 vs 真实可训练数据量差距大 | 真实可用率经验值 35-55%，估算需打折扣 |
| 长尾方言对齐模型缺失 | 强对齐错 → 训练数据脏 → 模型差 | 冷启动期人工校对比例提高；逐步建立方言专用对齐模型 |

### 6.2 商业风险

| 风险 | 缓解 |
|---|---|
| 标注产能不达预期 → 飞轮转不动 | 合同里写"模型升级速度与 B 实际标注量挂钩，不构成违约"。B 自带标注团队这条已大幅降低风险 |
| 验收口径扯皮 | 合同附件提供测试集 + 双方协商 CER 基线；以测试集为准而非主观满意度 |
| 模型权重归属争议 | 合同明确：**通用基座 + pipeline 代码** = Kevin 持有授权 B 使用；**B 数据训出的方言 LoRA 权重** = B 独占 |

### 6.3 合规边界（必须 B 承担主体责任）

| 法规 | 要求 | 责任划分 |
|---|---|---|
| 《个人信息保护法》第 55 条 | 含敏感个人信息的数据训练 AI 模型前须做 PIPIA（个人信息保护影响评估） | **B 主体责任**；Kevin 提供脱敏工具 |
| 《网络安全法》（2026-01-01 新版生效） | 网络产品和服务提供者合规义务 | **B 主体责任**（B 是直接服务终端用户的一方） |
| 用户授权 | 通话开头需告知"通话可能被录音和用于服务改进" + 留存授权日志 | **B 负责**用户告知与授权流程 |
| 敏感信息脱敏 | 人名 / 电话 / 身份证号 / 住址等替换为占位符后才能进训练集 | Kevin 提供自动脱敏 pipeline；B 负责脱敏规则配置 + 抽检 |
| 数据所有权 | 原始录音归 B；转写文本归 B；模型权重见上节 | 合同明确 |

**合同必加条款**：「乙方（Kevin）提供合规工具链。终端用户告知 / 授权 / 数据合规主体责任由甲方（B）承担。因甲方业务本身合规问题导致的连带责任，乙方不承担。」

### 6.4 边界外的事（明确不做）

- ❌ 不替 B 做电话 / SIP / CTI 系统建设（如 B 没有，建议外包专项）
- ❌ 不做完整客服中台（IVR / ACD / 工单系统）
- ❌ 不承担终端用户合规告知 / 授权流程
- ❌ 不承诺藏维蒙等独立语言的识别能力（v2 路线图）
- ❌ 不承担 B 业务侧违法的连带责任（如电销骚扰等）
