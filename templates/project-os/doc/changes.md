# 变更记录（CR / Change Request）

> **需求正文一旦冻结 = 只读**。任何需求 / AC / 字段 / scope 变更走 CR，按时间倒序追加在此（**append-only**，旧 CR 不改）。
> **AI §0 自检强制扫本文件**：发现涉及当前 ticket 的 CR → **以 CR 为准**（CR 覆盖需求正文）。
>
> **为什么国内 B 端必须双轨追踪**：客户"必改"是确定事件（改 xlsx / 改字段 / 砍 scope），
> 把它当异常处理会让 daily 裂成返工螺旋。CR 把"客户改了什么、覆盖哪个 ticket、谁签字"显式留底，
> 让 AI 与 reviewer 永远知道"现在以谁为准"。

---

## CR 模板（复制下面整段，填空，贴到「CR 列表」最上方）

```
## CR-YYYYMMDD-NN: <一句话变更标题>

- **提出人**：<Kevin / 客户 / Reviewer / AI 评审>
- **影响 ticket**：<id1>, <id2>（无则写"无新增，仅确认现状"）
- **背景**：<为什么要改——客户改了 xlsx / 实测撞墙 / 评审发现不一致>
- **变更前**：<引用被冻结正文的原段 或 ticket 原 AC>
- **变更后**：<新内容，能落地的具体值>
- **影响下游**：<连带改的表 / 字段 / 文档 / 其他 ticket，没有就省略>
- **决策**：✅ 接受 / ❌ 拒绝 / ⏸️ 待定
- **签字**：<谁> @ YYYY-MM-DD（<决策依据一句话；可附"X 可在 Y 时机改回"的回退条件>）
```

> **铁律**：
> 1. **before/after 都要有**——只写"改成 X"而不写"原来是什么"会让人看不懂为什么。
> 2. **必须有签字**——CR 是有人拍板的决策，不是 AI 自己改的笔记。
> 3. 客户原始材料 vs 推断设计冲突时，**客户原始材料优先**，并在 CR 里点明"以 origin/ 哪份为准"。
> 4. 一个 CR 若同时开了待答问题，**同步在 [`_oq.md`](_oq.md) 开一条 OQ 并互相引用**。
