# ADR 索引（&lt;&lt;PROJECT_NAME&gt;&gt;）

> Architecture Decision Records——架构 / 跨 ticket 模式决策。每份记录"**为什么这么选**"，
> **一次写完不维护变更历史**（要修订就写新 ADR 标 `Supersedes ADR-NNNN`）。
> ADR 的目的是让 5 个月后的新人（含 AI）看懂"曾经因为 X 所以 Y"，不是写设计长文。

## 何时引用 ADR（快速决策表）

> ticket prompt §0 自检强制："凡是 ADR 编号 ↔ 本 ticket 改动文件存在 import / extends / implements / DDL 引用 / 字段类型对齐 关系的，**读全文**。"
> 下面给"按场景判断该读哪些 ADR"的骨架，实例化后填真编号。

| ticket 场景 | 必读 ADR |
|---|---|
| 业务表设计 / 写迁移 | <多租户 / UNIQUE / 字段类型对齐字典 的 ADR> |
| 写后端 service | <service 基类 / 复用约定 的 ADR> |
| 权限 / 菜单 seed | <菜单分治 / 权限段分配 的 ADR> |
| 鉴权 / 上传 / 第三方集成 | <鉴权模式 / 存储直传 的 ADR> |

**不命中任何 ADR 的 ticket**：也要在 §0 自检行写明 `ADR: 无相关`（**强制声明**），不允许跳过——
显式声明"我查过没相关 ADR"，比默默不查可审计。

## §0.5 预检范式（ADR 如何变成 ticket 的前置门）

> ADR 不是"写完归档吃灰"。它通过 ticket prompt 的 **§0.5 预检** 强制被消费：

```
ticket prompt 结构（与 daily/ lane 的 prompt 模板对齐）：
├─ §0   运行时现场自检（读 PROJECT.md / changes.md 覆盖本 ticket 的 CR / authority SSOT）
├─ §0.5 预检：对照 _adr/README.md「何时引用」决策表，
│        列出本 ticket 命中的 ADR 编号并读全文；不命中显式写 "ADR: 无相关"
├─ §1.. 主任务（引用 schema §X / 组件 §Y，不自造）
└─ §N   贴 raw output + 验收结果
```

> **为什么放 §0.5**（在自检之后、主任务之前）：避免 AI 先写完再发现"撞了已决决策"返工。
> 决策在写代码前消费，是把 ADR 从"文档"变成"护栏"的关键。

## 写新 ADR 的触发条件（满足任一即起）

1. **跨 3+ ticket 反复撞同型问题**——同一种坑修了 3 次，说明缺一条全局约定（这是最高频的 ADR 来源）。
2. **一次重大架构选择需要"为什么不选 X"留底**——如框架部署形态、是否引入某中间件。
3. **V1 / V2 阶段切换的边界**——本期先 disable / mock，下期再开，蓝图写进 ADR 防丢。

## 不要为以下情况起 ADR（负面清单，防 ADR 通胀）

- ❌ **单 ticket 内的实现选择**——写 git commit message 即可。
- ❌ **一次性 hotfix**——进当天 daily 的 `_open-issues` / closing 决策即可。
- ❌ **临时变通**——5 个月后没人看得懂的"曾经因为 X 所以 Y"，不值得占一个编号。
- ❌ **栈/框架的固有机制**——那是 [`../../stacks/`](../../stacks/) 栈插件的事，不是项目级架构决策。

---

## 维护约定（防 ADR 变成过度设计）

- 写完 1 次后**不改正文**（除明显错字）；修订写新 ADR 标 `Supersedes ADR-NNNN`。
- **不写**"备选方案对比 / 未来扩展 / 替代方案"长篇——决策必要的取舍写在「§3 后果」即可。
- **不写**"主持人 / 时间盒 / 与会者"——异步执行，无 meeting。
- ADR 模板见各 `NNNN-*.md`（建议段：上下文 / 决策 / 后果，三段足够）。
