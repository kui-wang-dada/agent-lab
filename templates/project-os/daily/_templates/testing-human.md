## §Solo —— 一人模式退化路径（`<<TEAM_MODEL>>` 是单人时用）

> 没有三全栈交叉时，**别凑三人形式主义**，但也别跳过感官层。一人 + AI 的最小有效闭环：
>
> 1. **自己跑一遍 app**：按上面 §1+ 的 happy path + 至少 1 个反例，**真点一遍**（不是看代码想象）。
> 2. **截图自检**：每个关键页截图，AI 协助对照 `doc/authority/components-ssot.md` 真截图锚定做 diff（治视觉偏差的根：复盘里视觉偏差源于"靠字段表脑补 UI"，真截图比对才挡得住）。`<<STACK_FRONTEND>>` web 端用浏览器截图；`<<STACK_APP>>` 端用其对应工具截图（命令见 `stacks/<<本栈>>-notes.md` §screenshot）。
> 3. **DB 表树肉眼对照** `doc/authority/schema-ssot.md`（仍是人点鼠标的活）。
> 4. 发现偏差：**能当场解决的当场交 AI fix → 重测闭环**；只有**无法及时解决 / 需决策**的才 append `_open-issues.md`（触发者写"solo"），closing 一并决策。
>
> **关掉条件**：纯机械改 / 无 UI 面的 ticket → §Solo 只跑 DB/数据对照，截图步骤跳过。

## 给 AI 生成 testing-human.md 时的填表指南（closing 时 AI 用本模板生成次日）

**0. 写给非开发的测试人员看（最高原则）**：
- **大白话**："点哪里 → 看到什么"。控件名"下拉/数字键盘/日期选择"可以；**技术黑话不准**（组件类名 / 事件机制 / ORM 写法 / 框架注解都不写进测试点）。
- **不写实现背景**：段顶不要"复用 X 组件 / 详 reports / 怎么实现"——那是 reports/testing-ai 的事。段顶只留"前置数据准备"。
- **不做角色登录测试**：统一最高权限账号跑完（§0 已声明），角色权限本期不测。app 端按角色门控的页除外（段顶注明账号）。
- **删方法论段**：不写"假装某角色身份"这类绕的元规则（核心诉求已在 §0 通用规则说清）。
- **命令式可断言的一律不写进人测**（DB 字段对照 / 字典计数 / 菜单·权限行数 / 接口返回码 / 编译，AI 已在 testing-ai 跑过）；人力只聚焦"看一眼 / 用一下 / 凭直觉"的事。
- **§N 段按数据依赖链排序**：上游产数据的段排前、下游消数据的段排后，让测试员从上往下跑、每段数据正好是前段产出，不用造假数据。段顶"前置数据准备"标"产出 X 供 §M" + "依赖 §K 产出"，让顺序意图显式。

1. **§N 内只用 `| 编号 | 测试点 |` 表格**，不分多栏目（栏目易同质化）。
2. **每编号项一行说清**（菜单路径 / 关键字段 / 期望结果），不展开成子 bullet。
3. **共性规则在 §0 一次说清**，ticket 段不重复。
4. **编号体系全局唯一（反复翻车点）**：段头 `## §N <TICKET>`，**N = 该 ticket 在当日 README 任务清单行序**；条目 `N.1/N.2...`（**不是每段从 1 重数**）；联调段 `C.1/C.2`。
   > ⚠️ **为什么老犯**：testing-human 是 N 个 ticket agent **各自独立 append** 拼出来的，每个只看见自己段、不知是第几个 → 默认从 1 数、丢 §N。**让 N 个独立 agent 拼出连续编号，结构上不可能。** 两道防线缺一不可：① 写入侧 每个 ticket agent 段头用 README 行序当 N（prompt 模板已强制，agent 自己能算）；② closing 兜底 必跑"单人汇编重排"（见 audit E.5）——永远要一个收口的人/步骤。
   > **绝对规则**：条目编号 `N.Y` 的 **N = 该 ticket 在当日 README 任务清单的行序**，Y 在本段内从 1 递增；**严禁每段从 1.1 重数**。这是反复翻车的头号点，写入侧 + closing 兜底两道防线都不能省。
5. **每 ticket 只覆盖主链路 + 感官，3-6 项**：入口可达 / 核心 happy path / 1-2 个关键反例 / 视觉对照真截图 / 跨端一致（若涉及）。**DB 字段对照 / 字典计数 / 菜单·权限行数一律归 testing-ai，不写进人测。**超 6 项 = 多半混进了机器可断言项，回收。
6. **行数目标**：5 ticket 一天 ≤ 80 行。
7. **每编号项必含具体**：菜单路径或板块+卡片名 / 字段名或字典 key / 期望具体值（"6 条" / "中文 label 无英文 raw"）。
8. **反例必带**：每段至少 1-2 个反例（必填空 / 业务约束 / 权限）。
9. **DB 字段对照 / 字典计数 / 菜单·权限行数一律归 testing-ai，不写进人测**（这些机器可断言，AI 已跑）。人测段不出现"DB 表树字段对齐""字典 N 条对应""菜单父 + N 行"这类条目。
10. **总原则（最高）**：**人测的唯一目的是测主链路 + 抓机器断言不了的感官问题；可机器断言的全归 testing-ai。问题当场解决，不攒。**人测抛出的问题能当场修的当场交 AI fix → 重测闭环；只有无法及时解决 / 需决策的才进 `_open-issues.md`。
11. **前置数据依赖必显式写**：happy path 依赖上游 ticket 数据时，段顶加 `**前置数据准备**` 块，列"去哪 → 录什么 → 数量/日期/登录人约束"，避免测试员卡在"无可用 X"反复 raise。
